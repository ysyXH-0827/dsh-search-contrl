## 五、速度实验日志（每次月报至少一次：假设 → 测量 → 采纳/否决）

### 实验 1：链接校验，无界并发 vs 有界并发+重试+缓存（5 月 45 条链接实测）

| 策略 | 耗时 | 成功 | 429 | 结论 |
| --- | --- | --- | --- | --- |
| A 无界 Promise.all（基线） | **475 ms** | 40/45 | **5** | 快 1.26 s，但 11% 假阴性 |
| B 有界并发 6 + 429 退避重试 | 1,731 ms | **45/45** | 0 | 慢 1.26 s，零假阴性 |
| C B + 24h 结果缓存（热） | **5 ms** | 45/45 | 0 | 重复月份近乎免费 |

- **假设**：并发越高越快，因此无界最优。
- **测量**：无界确实快 1.26 s，但产生 5 条 429；这 5 条必须串行复测（每条约 1.5 s），实际代价 **+7.5 s**。
- **结论**：**采纳 B + C**。无界并发只在“愿意人工复测 429”时使用；默认走有界 + 重试 + 缓存，净收益约 **+6.2 s**。
- **工具**：`scripts/verify-links.mjs`（`--concurrency`、`--retries`、`--cache-hours`）。

### 2026-10-23 设置页 GUI（1.5.0）

- **结果**：新增渲染进程配置页，支持自定义搜索源、自定义主题（不限科技）、博主主页链接定向检索；所有写入都可回退。
- **可回退的实现**：不是「保存前备份」，而是 **保存时先把被替换的旧版本写进 `history/<ISO>.json`，再写 `settings.json`**；重置与回退走同一条路径 —— 于是「回退」这个动作本身也会被快照，点错一次还能再退回来。
- **不写 profile patch 的原因**：profile 的 `cordis.patch.yml` 是 Host 合成的配置层，插件运行期改写它等于让 Host 和插件同时改同一份文件，冲突无解；自带 `settings.json` + 历史目录才是可回退的边界。数据目录 `~/.dsh/plugin-data/<id>/`，可用 `SEARCH_CONTRL_DATA_DIR` 覆盖。
- **规律**：**凡是要「可回退」的功能，回退动作本身必须被记录**；只备份写前状态的回退是一次性的。

### 无浏览器怎么测渲染进程 bundle

- **问题**：设置页代码在浏览器里跑，profile 的 `node_modules` 没有 `react`，无法直接 SSR 或浅渲染；真跑起来只能靠人肉点。
- **做法**：`scripts/test-client.mjs` 用 stub 的 `react`（`useState`/`useCallback`/`useEffect`/`createElement`）+ stub 的 `react/jsx-runtime` 造一个假 `require`，把 `lib/client.js` 源码用 `new Function('window', source)` 塞进假 `window.__ModuleLoader__`，然后断言 **模块 id、`exports.apply`/`exports.inject`、slot 名与 key、summary 文案、卡片树里的各 tab 与按钮文案、平台解析映射**。
- **取舍**：这不是渲染测试，不验证像素与交互；验证的是「注册契约 + 结构 + 文案」，正好是插件装上后最容易炸、也最不容易在浏览器里定位的部分。
- **规律**：**渲染进程代码也要有可自动化的契约测试**，否则每次改动都得重启 Host 人肉点一遍，回归成本高到不会去做。

### 「设置里看不见」：plugins.row.config 不是设置侧边栏

- **症状**：客户端 bundle 注册成功、插件行配置页也在，但用户在「设置」左侧导航里看不到任何东西。
- **根因**：DSH 里这是两个不同的 slot。`plugins.row.config` 只挂到 **插件行**（设置 → 插件 → 该插件）的配置视图；要让条目出现在**设置窗口左侧的一级导航**，必须注册 `settings.section`。
- **做法**：`ctx.slots.inject('settings.section', () => ctx.slots.register({ name: 'settings.section', id: '<唯一 id>', order: <数值>, label: '搜索控制' }, Component))`；同时 `package.json` 的 `dsh.client.inject` 要声明 `@deepseek-ai/dsh-client-ui-settings` 与 `@deepseek-ai/dsh-client-ui-slots`，否则渲染进程拿不到设置窗口提供的运行环境。`order` 决定排序：已装插件的分区占 100–151，本插件取 152。
- **保留两个入口**：同一张卡片同时挂 `settings.section`（一级分区，`page: true`）与 `plugins.row.config`（行配置页，summary 折叠形态），用户从哪进都能改。
- **规律**：**"注册成功"不等于"出现在用户找的位置"**——交付前先问：用户会去哪个界面找它，那个界面对应哪个 slot？

### 改名是一次跨层重构，不是 sed

把 `tech-daily-report` 改成 `DSH-Search-Contrl` 时，一个名字同时出现在 **7 个不相干的层**：npm 包名、技能注册名、工具名（模型可见）、patch 行 id（profile 配置）、客户端 slot id、HTTP 桥前缀、数据目录路径。漏掉任何一层都不是「显示不对」，而是**整条链路断掉**——桥前缀只改服务端，设置页所有请求 404；只改客户端 bundle 的 module id，loader 按包名找不到模块。

两个踩过的坑：
- 批量替换要**长串优先**。先替换 `tech-daily-report` 再替换更长的 `tech-daily-report-search-control`，后者永远不会命中，只会留下 `search-contrl-search-control` 这种怪 id。顺序错了测试会抓到，但要先写断言。
- 改完必须同时验证**单侧自洽**和**跨侧一致**：客户端与服务端各 grep 一次桥前缀，测试里断言 `settings.section` 的 id、row key、module id、包名四处同名。

规律：**重命名后先跑一次"名字矩阵"检查**（每个名字至少两处引用：定义处 + 使用处），比逐个回忆哪里用过可靠。

### 抓 Cookie 必须在 Host 侧，渲染进程永远做不到

第一次设计「点击获取 Cookie」时想的是在设置页里加密钥：走不通，因为**设置页是渲染进程**，跨域 HttpOnly Cookie 对它是不可见的，任何 `document.cookie` 取法只能拿到当前页自己的非 HttpOnly 项。结论：抓 Cookie 只能在 Host 进程做，页面只负责点按钮和显示状态。

落地方式是 **Chrome DevTools 协议**，而不是扩展或让用户手抄：
1. Host 用独立临时 `--user-data-dir` 启动浏览器，跳到登录页；
2. 轮询 `Network.getAllCookies`（每 1.5 秒），直到站点要求的**必需 Cookie 名**全部出现；
3. 关窗、删临时 profile、只保留必需项写入 `0600` 文件。

三个必须写进代码的边界：超时（5 分钟）要关窗且不落盘；同一时刻只允许一个捕获会话（否则两个窗口抢同一个 jar）；Cookie 值绝不回传页面（只回名字与掩码），否则“设置页”就成了凭据泄露面。

### 判断"登录成功"要看必需 Cookie 名，不要看页面状态

最初想等窗口 URL 跳到首页就算登录完成——不可靠：很多站点登录后停在中间页，或者跳转前就要二次验证。改成读 CDP 拿到的 Cookie 列表、检查该站点的必需名（B站 `SESSDATA`、知乎 `z_c0`…）全部存在才算成功。这样"页面打开了但没登录"不会被误判成已登录，也不会把半截会话写进 jar。

### 2.1.1 「登录了却没抓到 Cookie」：CDP 方法选错，且错误被当成"还没启动"

现象：用户在登录窗口里完成登录，设置页一直显示"等待登录…"，5 分钟后超时，什么都没保存。

实测（Edge 141，`--remote-debugging-port` 打开的临时 profile）：

| 调用 | 结果 |
| --- | --- |
| `/json/version` 返回的 **browser** target 上 `Network.getAllCookies` | 报错 `-32601 "'Network.getAllCookies' wasn't found"` |
| **browser** target 上 `Storage.getCookies` | 正常返回全部 Cookie |
| attach 到 page target 后用 sessionId 发 `Network.getAllCookies` | 同样正常 |

根因有两层：① 选的方法在 browser target 上根本不存在；② 轮询循环把所有异常都当成"调试端口还没起来"，真实错误被吞掉，用户只看到一直等待。

修法：

1. 先试 browser target 的 `Storage.getCookies`，失败再 attach page target 用 `Network.getAllCookies` 带 sessionId。
2. 只把"连不上 / 没 socket url"归为可重试（错误带 `code:'not-ready'`）；方法或权限错误立即返回 `code:'cdp-error'`，并把消息显示到设置页。
3. 加 `scripts/smoke-cdp.mjs`：真的开一个浏览器、真的种一个 SESSDATA、再让读取器找回来。单测只能证明逻辑，证明不了浏览器行为。

规律：**凡是依赖外部程序协议的功能，必须有"真进程烟测"，且错误分类要区分"还没好"与"永远不会好"。**


### 2.1.2 「EPERM, Permission denied」：杀进程≠目录已释放

症状：点「获取 Cookie」、登录成功，界面却报
`EPERM, Permission denied: \\?\C:\Users\...\Temp\dsh-search-contrl-bilibili-1792765757383`。

根因不是权限配置，是时序：

| 步骤 | 实际发生的事 |
| --- | --- |
| `handle.kill()` | 只杀了浏览器主进程 |
| 紧接着 `fs.rmSync(profileDir)` | Edge 的 renderer / GPU / crashpad helper 还持有该目录 → EPERM |
| `finally` 里抛出 | 覆盖了已经成功的读取结果，用户只看到裸错误 |

修法（三条一起才完整）：

1. **等真正退出再删**：`defaultLaunch` 返回 `exited` Promise（`exit`/`close` 事件 + 15s 兜底），`stopBrowser()` 先 kill 再 `Promise.race([exited, sleep(6s)])`。
2. **Windows 要杀进程树**：`spawn('taskkill', ['/PID', pid, '/T', '/F'])`；只 `child.kill()` 会留下持有句柄的 helper。
3. **清理失败不许影响结果**：`removeProfileDir()` 指数退避重试 8 次（250ms×attempt），永不抛，失败只写进 `state.cleanup`；下次捕获开头用 `sweepProfiles()` 清超过 30 分钟的残留。

规律：**清理是 best-effort，捕获结果才是交付物。** 任何 teardown 都不得把成功结果改写成失败。

烟测要覆盖清理：`scripts/smoke-cdp.mjs` 现在真开 Edge、真种 Cookie、读完后再走 `stopBrowser` + `removeProfileDir`，输出 `cleanup ok = true` 与 `CLEANUP OK`。


### 2.1.3 「博主最新视频」拿不到：签名接口才是可靠路径

症状：登录 Cookie 已存好，`action:'blogger'` 却退回搜索引擎结果，拿不到真正的最新视频。

两个独立故障叠在一起：

| 故障 | 证据 | 修法 |
| --- | --- | --- |
| 未签名的 `x/space/arc/search` 被风控 | `{"code":-799,"message":"请求过于频繁"}`（已登录也一样） | 改走 **WBI 签名** 的 `x/space/wbi/arc/search`，并带上 `dm_img_list`/`dm_img_str`/`dm_cover_img_str` 指纹占位参数；未签名版只作兜底，中间退避 1.2s |
| 补丁插错分支 | 快速路径文本同时匹配到 topic 与 blogger 两处锚点，topic 分支里多出一份引用 `steps`/`blogger` 的死代码 → `steps is not defined` | 补丁只替换首处 / 用唯一锚点；加静态回归测试断言 `createBilibiliClient({ cookie: cookieHeader })` 只出现 1 次、`steps.push` 为 0 |

登录态带来的额外收获：`view/conclusion/get`（同样要 WBI 签名）能拿到平台 AI 总结——这只在登录 Cookie 下可用，匿名访问返回 `-101`。

规律：**外部 API 的"公开"端点不等于"可用"端点**；风控靠签名而不只是 Cookie，所以签名逻辑要跟登录态一起做。

### 2.1.6 「history is capped」只在 CI 挂：同毫秒写入把快照吃掉了

本地跑绿、CI 跑红的一次 flaky，根因不是环境差异，是**测试依赖了真实时钟的分辨率**。

`saveSettings()` 用 `new Date().toISOString()` 当快照文件名（精确到毫秒）。7 次背靠背保存只要有两对落在同一毫秒，后一次就把前一次的快照文件覆盖掉：

| 场景 | 快照文件数 | `listHistory().length` |
| --- | --- | --- |
| 每次保存都不撞毫秒 | 6 | 裁剪到 3 → **3** |
| 第 5、6 次撞同一毫秒 | 5 → 覆盖后 4 | 裁剪到 3 后又被覆盖 → **2** |

CI 的 runner 比本机快，撞毫秒的概率高得多，于是同一条断言本地 5 连绿、CI 一次红。

**修法两层，缺一不可：**

1. 存储层不再依赖唯一毫秒：`uniqueSnapshotName()` 发现同名就加 `-2`、`-3` 后缀；`compareSnapshotNames()` 解析后缀做“新在前”排序，保证裁剪砍的是最旧的那份。
2. 测试层不再赌时钟：裁剪用例显式传 `now`（`Date.UTC(2026, 0, 1, 0, 0, 0, i)`），并新增两条用例锁住行为——「同毫秒三次保存必须有 2 个互不相同的快照」（首次保存无前版本，故是 n-1）和「同毫秒时最新的那条排在最前」。

**规律：任何“看起来是环境问题”的偶发失败，先查它是否依赖了不可控的分辨率——时钟、文件系统排序、端口、并发调度。测试要把这些量变成入参。**

### 2.1.4 「速度有点慢」：缓存放错了层，退避不分错误类型

用户反馈一句话：“速度有点慢”。实测冷启动一次「博主最新视频 + AI 总结」的分解：

| 步骤 | 耗时 | 是否必要 |
| --- | --- | --- |
| `nav` 取 WBI 密钥 | 113 ms | 每 10 分钟一次就够 |
| `x/space/wbi/arc/search` 列表 | 352 ms | 60 秒内可复用 |
| `x/web-interface/view` 详情 | 72 ms | 同一条视频可复用 |
| `view/conclusion/get` AI 总结 | 181 ms | 同一条视频可复用 |

三个真实原因：

1. **缓存放错层**：`createBilibiliClient` 每次工具调用都新建，缓存挂在实例上等于没有缓存；
2. **AI 总结又取了一次 `nav`**：`latestVideos` 取过密钥，`aiConclusion` 再取一次，白花 113 ms；
3. **退避不分错误**：签名请求失败后无条件 `sleepImpl(1200)` 再回退，只有 `-799`（频率限制）值得等，`-412` 这类风控拒绝应当立刻走下一步。

修法：缓存提到**模块级**（密钥 10 分钟、列表 60 秒、详情/总结 10 分钟）、密钥用 `Promise` 记忆化、`await sleepImpl(1200)` 用 `if (message.includes('-799'))` 包起来。

效果：冷启动 803 ms（4 个必要请求），同一问答第二次 1 ms。

规律：**缓存的位置必须和“调用粒度”对齐**——工具每次调用都新建对象时，实例内缓存等于装饰。

### tag 触发的 workflow 用的是 tag 所在提交的文件版本

补打 `v2.1.6` / `v2.1.7` 两个历史 tag 后，Actions 立刻各起了一个 publish run，两次都 `npm error You cannot publish over the previously published versions` 失败。

原因不是隐藏的发布逻辑，而是 GitHub Actions 的取值规则：**`push: tags` 触发时，`uses:`/`run:` 用的 workflow 文件来自被推的那个 tag 指向的提交**，不是默认分支的最新版。这两个 tag 指向的提交里 `publish.yml` 还没有「版本已存在就跳过」的守卫，所以重放必然重发、必然 403。

三条可用结论：

1. workflow 的修复只对**之后的 tag**生效；给历史提交补 tag 不会继承新守卫。
2. 需要一个 tag 重跑安全时，tag 必须指到包含守卫的那个提交之后。
3. 补打历史 tag 前先想清楚：它会不会触发一次注定失败的发布 run。要保留 tag 又不想跑 CI，就把标签当作纯书签，发布只走 `workflow_dispatch`。
